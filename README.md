# 投标智能体

**让每一条投标响应都能找到依据，让每一处修改都由人决定。**

投标智能体是一个本地桌面工作台，帮助编标人员把招标要求、企业资料、技术文件、章节草稿和人工复核放在同一条工作链中。产品采用 Electron、React、TypeScript 和 Word 文档处理架构。

项目目前重点解决两类工作：**审查已有技术标**，以及**为新项目建立有证据的响应草稿**。它组合程序规则、可选的模型分析和人工确认。报告中的“待核实”是一种正式结果：缺少证据时，系统不会替用户作出符合要求的承诺。

## 项目特色

### 从招标要求出发，而不是先生成一篇文章

导入招标文件后，工作台整理可编辑的《招标要求清单》，识别资格、商务、技术、评分及否决类条款。要求保留原文和文件位置；如果来源无法可靠定位，就标记位置缺失，不编造页码。导入企业资料后，系统逐项形成响应矩阵，列出要求、候选证据、判断与待处理事项。

中文强制条件，例如“必须”“应当”“不得”“至少”“不超过”，有专门的规则识别。对能够明确比较的数值、日期和有效期，优先由本地程序计算；没有找到资料时保持“待核实”，不会自动写成“满足”或“不满足”。

### 证据与结论放在一起

审查结果尽量附上原文、来源文件和段落、行或表格位置。已有施工技术文件的体检先抽取结构化事实和候选冲突，再按规则复核。可选的模型语义复核只对候选原文片段提出关联建议，数量和单位仍由本地程序检查。用户可以接受、排除或撤销模型建议。

体检区分**明确矛盾、疑似不一致、证据不足、无问题**。两个数字可能分别代表不同的统计口径；口径未查明前，报告提示核对，不直接认定其中一个错误。

### 保留原 Word 文档，支持局部修订

施工技术文件体检可以读取 DOCX 的章节、正文、表格及文档内的媒体关系，展示可定位的内容，并导出 Word 体检报告。章节优化目前聚焦可验证的局部修改：显示原文与表格、暂存修订、人工确认后写入导出的原文副本。包含图片、域或链接等复杂元素的段落会提示在 Word 中处理，以降低破坏原有结构的风险。导出后仍需用 Word 检查排版、附件与签章。

### 逐章编写，保留人工控制权

新项目工作台可按要求类别建立章节草稿，关联招标原文和企业资料，支持逐章编辑、保存、确认与撤销。来源发生变化后，已有判断会提示失效；缺少招标或企业证据定位的章节不能直接确认。业务 Skill 以可编辑模板呈现给员工，用来固定工作步骤，不额外引入一套 Agent 运行时。

技术标模块还提供招标分析、目录生成、全局事实设定、正文编辑和 Word 导出等能力。不同入口的成熟度并不相同，章节草稿不等于已经完成的正式投标文件。

### 模型由用户选择，敏感资料由用户控制

在 **设置 → AI 模型** 中，可添加 OpenAI-compatible 服务：自行填写 Provider 名称、Base URL、模型 ID、API Key 和请求参数，也可连接兼容接口的本地服务。文本模型与图片模型分别配置，并可按业务任务选择模型。模型目录接口不可用时，仍可手动填写模型 ID。

应用服务层使用 Windows/Electron 的安全存储能力保存密钥；安全存储不可用时，不会静默以明文保存远程密钥。连接测试发送不含业务资料的最小请求，但服务商仍可能收费。**真实客户资料默认在本地处理；调用云端模型前，须由用户确认接收方、传输范围与授权。**仓库不包含 API Key，也不把模拟响应标成真实模型验证。

## 两条主要工作流

| 场景 | 操作顺序 | 当前可得到的结果 |
| --- | --- | --- |
| 已有技术标审查 | 导入 DOCX → 查看文档结构 → 全文体检 → 查看证据 → 人工确认 → 局部修订 → 导出 Word | 带来源位置的体检结果、人工决定、体检报告和局部修订副本 |
| 新项目编标准备 | 导入招标文件与企业资料 → 编辑要求清单 → 查看响应矩阵 → 建立章节草稿 → 风险复核 → 导出 Word | 要求、证据、待核实事项、逐章工作稿及核验报告 |

第二条工作流目前适合形成**可核验的编标底稿**。正式技术标还需要核对招标原件、图纸、企业资质、报价、工期和合同承诺，并完成专业编写与人工签批。

## 当前可用能力

- 导入招标文件与企业资料，形成可编辑的要求清单和响应矩阵；缺少证据时标记“待核实”。
- 对可明确比较的数值和日期使用程序规则，保留招标原文及企业资料的位置。
- 按要求类别建立逐章响应草稿，支持编辑、保存、人工确认和撤销；删除来源引用后不能确认该章。
- 对已有施工技术文件开展本地结构解析、问题体检、局部修订和 Word 导出。
- 在“设置 → AI 模型”中配置自己的模型服务。支持手填模型 ID 和 OpenAI 兼容地址；密钥由应用服务层保存和使用。

| 能力 | 状态 | 验证边界 |
| --- | --- | --- |
| DOCX 结构读取、施工技术文件规则体检、局部修订与 Word 导出 | 已实现 | 真实案例曾用于本地解析和回归；公开仓库不包含客户原件 |
| 招标要求清单、企业资料对照、响应矩阵、风险提示 | 已实现基础流程 | 规则能处理部分中文强制条件、数字和日期；复杂语义仍需人工判断 |
| 章节草稿编辑、保存、确认、撤销及来源失效提醒 | 已实现 | 草稿是编写起点，不是可直接提交的完整标书 |
| 可选模型语义复核、BYOK 配置与连接诊断 | 已实现接口与本地测试 | 真实第三方模型效果取决于用户凭证和授权，尚无通用质量保证 |
| 复杂图纸核验、工程承诺真实性、最终投标合规判定 | 尚未完成 | 需要项目原始材料、专业人员与外部核验 |

公开测试使用合成材料，覆盖部分要求识别、来源引用、状态判断、模型配置及服务层行为。小样本测试通过**不代表**在任意行业、任意招标文件上的准确率。真实项目使用前，仍应由编标人员复查每项结论。

## 使用边界

逐章草稿是证据整理和人工编写的起点，不是自动完成的正式投标文件。施工参数、资质、价格、工期和服务承诺必须由经办人核实。未提供招标文件、图纸或企业原件时，软件不能替代这些材料的审查。真实客户文件不要提交到本仓库；使用外部模型前应确认数据传输范围和授权。

本项目不预测评标分数，不凭模型自然语言输出宣称完成合规审核。真实客户资料不会因为导入本地工作台而自动获得公开分发授权。

## 技术结构

```text
client/
├── src/                    React / TypeScript 界面与业务入口
├── electron/               Electron 主进程、IPC、本地服务与文档处理
├── scripts/                构建、检查与合成数据评测脚本
├── legal/                  打包进入应用的许可证与归属文件
└── product-branding.json   统一的产品显示名称
```

界面通过受控 IPC 调用本地服务。模型密钥和模型请求由应用服务层管理。部分历史兼容字段及独立授权机制仍存在；后续处理必须兼顾用户数据兼容与合法授权。

## 本地开发

Windows 开发基线为 Node.js 22。进入 client 目录后运行：

    npm ci
    npm run build
    npm run dev

应用主体位于 client/：Electron Main 与 Preload 负责本地服务和文件操作，React/TypeScript 负责界面。运行中的个人配置、密钥、客户文件和导出件不应提交到 Git。`npm run dev` 启动桌面开发版；不依赖模型的文档查看和本地规则功能可以先使用。运行前请阅读 [客户端开发说明](./client/开发说明.md)。

可针对近期改动运行：

    node scripts/evaluate-construction-coverage.cjs
    node --test electron/services/manufacturingWorkbench.test.cjs electron/services/modelProviderStore.test.cjs
    npm run smoke:electron-native

以上命令在 client/ 目录执行。合成测试数据位于 client/scripts/fixtures/；真实凤台案例文件不包含在本仓库中。
